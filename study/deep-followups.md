# 프로젝트를 이해하고 설명하는 연습

이 자료의 질문은 직접 만든 연습 질문입니다. 실제 평가 문항이나 공식 채점 기준을 재현하지 않습니다. 공유가 허용된 연습용 프로젝트로 사용하세요. 실제 후속 서술형 응시 중에는 AI·외부 자료를 사용하지 않고 본인이 직접 답합니다. 각 응시 환경의 안내가 우선합니다.

## 가장 먼저 연습할 여섯 질문

### 1. 문제 정의와 주도성

사용자가 겪는 실제 문제는 무엇이었나요? 담당자가 요구한 내용, 자료로 확인한 사실, 본인이 선택한 구현 범위를 구분하고, 그 선택이 결과물 어디에 반영됐는지 설명하세요.

### 2. 데이터와 처리 흐름

입력 항목 하나가 최종 결과에 이르는 과정을 추적하세요. 어떤 파일과 식별자를 연결하고 어떤 규칙을 검사하나요? 자료를 읽는 단계, 계산하는 단계, 화면에 표시하는 단계를 구분하세요.

### 3. 선택한 방법과 대안

핵심 처리 방법 하나를 골라 대안 하나와 비교하세요. 시간·정확성·실행 환경 중 어떤 조건 때문에 현재 방법을 선택했나요? 어떤 입력에서는 불리하거나 실패할 수 있나요?

### 4. 검증의 증거와 범위

결과가 맞다는 판단에 가장 도움이 된 실제 검증 하나를 입력·예상·관측 결과 순서로 설명하세요. 그 검사로 발견할 수 없는 오류와 추가로 필요한 검사는 무엇인가요?

### 5. AI 제안에 대한 본인의 판단

AI의 제안 중 확인·수정·거절한 사례 하나를 근거와 함께 설명하세요. 그런 사례가 없다면 받아들인 제안 하나와 그것이 타당하다고 판단한 근거, 아직 확인하지 못한 점을 설명하세요.

### 6. 조건 변경의 영향

가상의 변경으로 필수 조건 하나가 달라진다고 합시다. 어떤 입력·계산·화면·검증을 다시 확인해야 하나요? 숫자 하나만 바꾸면 충분한지 판단하고 우선순위를 설명하세요.

## 같은 관점을 다른 각도에서 묻는 열두 질문

### 7. 요구사항의 모호함

처음에는 불명확했지만 질문을 통해 확정한 조건 하나는 무엇인가요? 확인하지 않고 구현했다면 어떤 결과가 달라졌을까요?

### 8. 의견과 필수 규칙

담당자의 선호나 의견을 반드시 지켜야 하는 규칙과 어떻게 구분했나요? 충돌하는 요구를 발견했다면 어떤 근거로 조정했나요?

### 9. 데이터의 단위

자료의 한 행과 주요 수치의 단위를 설명하세요. 행의 의미나 단위를 잘못 이해하면 어떤 결과가 틀릴 수 있으며, 본인은 어떻게 확인했나요?

### 10. 예외의 구분

잘못된 입력, 정상 입력에서 결과가 없는 경우, 현재 방법으로 해결하지 못한 경우를 어떻게 구분했나요? 각 경우에 사용자에게 무엇을 보여줘야 하나요?

### 11. 간단한 방법의 충분함

더 복잡한 기술을 사용하지 않고도 현재 방법으로 요구사항을 만족한다고 판단한 근거는 무엇인가요? 어느 수준으로 데이터나 요구가 늘어나면 방법을 바꿔야 할까요?

### 12. 공개 코드의 이해

공개 코드나 라이브러리를 썼다면 어떤 부분을 맡겼으며, 우리 입력과 규칙에 어떻게 연결했나요? 쓰지 않았다면 직접 구현을 선택한 이유와 그 부담을 설명하세요.

### 13. 예상 결과의 근거

테스트의 예상 결과를 어떻게 구했나요? 프로그램 출력과 독립적인 계산이나 업무 규칙이 있었나요? 출력값을 그대로 정답으로 사용하지 않았다는 근거는 무엇인가요?

### 14. 수정 후 재확인

오류를 수정한 뒤 기존 기능이 유지됐는지 어떤 사례로 확인했나요? 오류를 발견하지 않았다면 변경 후 다시 확인할 대표 사례를 설계하세요.

### 15. AI 요청의 효과

결과물에 가장 영향을 준 요청 하나를 골라 목적과 실제 반영 여부를 설명하세요. 요청을 보냈다는 사실과 결과가 반영됐다는 사실을 어떻게 구분했나요?

### 16. AI 설명과 실제 코드

AI가 설명한 동작이 코드나 실행 결과와 다른지 확인한 적이 있나요? 없다면 핵심 설명 하나를 어떻게 검토할지 실제 파일을 기준으로 설명하세요.

### 17. 시간이 줄어든 상황

가상으로 작업 시간이 절반으로 줄었다면 어떤 필수 기능과 검증을 유지하겠습니까? 줄일 작업과 그 영향을 근거로 설명하세요.

### 18. 인수인계와 남은 위험

다른 사람이 내일부터 결과물을 쓴다면 무엇부터 알려줘야 하나요? 실행 방법, 핵심 가정, 미완료 부분 중 실제 사용에 가장 큰 영향을 주는 항목을 설명하세요.

## 답변을 구성하는 네 요소

답변은 아래 요소를 질문에 맞게 연결합니다. 모든 질문에 같은 문장을 반복할 필요는 없습니다.

1. **판단:** 무엇을 했거나 무엇이라고 판단했는가?
2. **근거:** 어느 자료·담당자 답변·파일·함수·실행 기록을 근거로 삼았는가?
3. **검증:** 어떤 입력에서 무엇을 예상했고 실제 무엇을 관측했는가?
4. **한계:** 확인하지 못한 부분은 무엇이며 어떤 조건이 바뀌면 다시 확인해야 하는가?

짧은 구조:

```text
[선택 또는 판단]했습니다.
[자료·규칙·관측]을 근거로 삼았고, [대안]과 비교해 [이유]로 선택했습니다.
[입력]에서 [예상]과 [실제 결과]를 대조했습니다.
다만 [미확인 사항·한계]가 남아, [추가 검사 또는 개선]이 필요합니다.
```

빈칸을 꾸며 채우지 마세요. 실제 근거가 없는 요소는 미확인이라고 밝힙니다.

## 모르는 내용이나 미완료 부분을 질문받았을 때

- **구현하지 않은 기능:** 현재 제출물에는 해당 기능이 없습니다. 현재 어디까지 구현했는지 설명하고, 추가할 처리와 검증을 구분합니다.
- **실행하지 않은 테스트:** 실제로 실행하지 않았다고 먼저 밝힙니다. 지금 설계할 수 있는 입력·예상 결과와 관측한 사실을 나눠 설명합니다.
- **AI가 선택했지만 이유를 모르는 방법:** AI 제안을 사용했다는 사실을 밝히고, 본인이 확인한 동작과 이해하지 못한 부분을 구분합니다. 알고 있다고 꾸미지 않습니다.
- **질문의 전제가 실제 작업과 다름:** 해당 방법이나 검증을 수행하지 않았음을 설명하고, 실제 사용한 방법과 근거로 답합니다.
- **기억나지 않는 정확한 숫자:** 수치를 만들어 말하지 않습니다. 기억나는 계산 방법과 확인한 자료, 수치 확인이 필요한 부분을 구분합니다.
- **반례를 지적받음:** 기존 판단을 방어하기보다 반례가 어느 조건을 깨는지 설명하고 영향·수정·재검증 순서를 제안합니다.

## 작업하면서 남길 짧은 메모

중요한 결정 두세 개만 기록해도 답변의 근거를 찾기 쉬워집니다.

| 결정 | 근거 | 고려한 대안 | 실제 확인 | 남은 한계 |
|---|---|---|---|---|
| 내가 정한 처리나 범위 | 파일·항목·담당자 답변 | 다른 방법과 제외 이유 | 입력·예상·관측 | 미확인 조건과 영향 |

요구사항, 판단, 검증 기록은 작업 중 허용된 범위에서 남깁니다. 실제 후속 문항 단계에서 기록을 열람할 수 있는지는 해당 안내를 따르세요. 이 자료는 후속 문항 중 메모나 AI에 접근할 수 있다고 가정하지 않습니다.

## 시간이 적을 때의 연습 순서

1. 연습 프로젝트의 목적과 필수 결과물을 한 문장씩 말합니다.
2. 실제 입력 한 건을 골라 결과까지 흐름을 말합니다.
3. 중요한 선택 하나를 대안과 비교합니다.
4. 실제 검증 하나와 미검증 한 가지를 말합니다.
5. 위 첫 여섯 질문에 각각 짧게 답하고 모르는 부분을 표시합니다.
6. 코치 프롬프트로 한 문항씩 추가 질문을 받거나 스스로 꼬리 질문을 만듭니다.

목표는 문장 암기가 아니라 본인의 파일·규칙·관측 결과를 연결해 설명하는 것입니다.
